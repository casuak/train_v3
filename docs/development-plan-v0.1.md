# 游戏开发规划 v0.1

需求基准：2026-09-28，Asia/Shanghai。

依据：《游戏设计文稿v0.1.md》及本轮补充的技术、美术、操作与登车战需求。

目标仓库：https://github.com/casuak/train_v3.git

本文件为开发建议稿。用户已经明确的要求与本文建议的首版参数分别列出；人数、地图规模、阈值、时间倍率和工期均可通过原型验证调整。本轮交付开发规划，工程初始化、代码提交与推送列入下文实施阶段。

## 1. 开发目标与已确定的约束

游戏核心是：经营一支持续迁徙的列车社会，依据物资、列车能力和变化中的世界选择路线，并在旅途中处理生活、生产与战斗。

| 领域 | 已确定要求 |
| --- | --- |
| 技术 | TypeScript + Three.js；使用 Git 管理版本，开发成果推送到上述仓库 |
| 游戏表现 | 横版 2D 正侧视剖面；美术素材使用图片生成能力制作 |
| 动画 | 使用骨骼动画，只制作行走、工作、轮轴转动等少量常用动作 |
| 工作管理 | 类似 RimWorld 的工作优先级安排 |
| 制作 | 右键工作台设置制作内容 |
| 强制行动 | 选择人物后，右键设施下达强制行动 |
| 自动生活 | 人物根据需求自动进食、睡觉恢复 |
| 战斗 | 敌人先登上车顶，在车顶交战；存活敌人可破入车厢，通常优先攻击车顶目标 |
| 战斗控制 | 人物征召后由玩家直接控制，解除征召后恢复日常行为 |
| 列车与世界 | 车厢内家具级布局；旅行时间持续推进车内模拟；铁路路线、环境和资源影响迁徙决策 |

建议首个平台为桌面浏览器、鼠标键盘、单机本地存档。桌面封装、多端同步和移动端操作不计入首个可玩版本。

## 2. 首个可玩版本的范围

目标是完成一段约 20—30 分钟的可重复试玩，验证经营、迁徙与登车战能互相影响。该时长是体验目标，需在试玩中调整。

| 内容 | 建议首版规模 | 完成标准 |
| --- | --- | --- |
| 列车 | 1 台机车 + 3 节功能可混搭的车厢 | 有连续通路，允许家具级布置；车厢能力影响旅行 |
| 人员 | 6 名乘员 | 各自具有饱食度、精力、生命、工作能力与优先级 |
| 基础设施 | 床、储物区、炉灶、工作台、维修点、供暖器、梯口/舱门 | 每种都有可用位置、交互位置、容量和状态 |
| 生产 | 做饭、制作维修材料、维修设施 | 食材/原料搬运、加工和成品入库形成完整链条 |
| 建设 | 放置、左右翻转、建造、拆除基础家具 | 花费资源和工时，更新通行状态，提示通路风险 |
| 工作 | 烹饪、制作、搬运、建造、维修 | 支持 0—4 级优先级、禁用、强制执行和取消 |
| 自动生活 | 自动找食物、吃饭、找床、睡觉 | 找不到资源时可降级处理并明确告警，不无限重试 |
| 战斗 | 1 类登车敌人，每波约 3—5 名；基础近战和 1 种远程武器 | 完成登车、车顶交战、破门、进入车厢的全过程 |
| 路线 | 6—8 个节点，至少 2 处路线选择，2 种环境条件 | 路线有旅行时间、燃料消耗、风险和补给差异 |
| 停靠 | 补给、简化交易、维修、获取新车厢的节点事件 | 停靠耗时，人物需求继续运行 |
| 扩张 | 1 次可获得额外车厢的事件 | 新空间提升能力，同时增加重量、消耗或维护负担 |
| 环境 | 日期、温度、基础供暖、一次可预报的寒潮/封线事件 | 准备不足会影响旅程，玩家有提前应对的机会 |
| 基础体验 | 暂停、1/2/3 倍速、存读档、事件通知、操作提示 | 一次试玩可以保存、退出、恢复并继续完成 |

原设计中的 20 人开局、60—100 人中期、200 人后期与 30—50 小时流程，作为长期方向，不能直接作为首版开发规模。

首版暂缓：复杂人物关系、家庭与故乡事件、详细疾病系统、派系外交、完整大陆生成、多年世界衰退、大型城市步行探索、复杂驾驶物理、多人联机。

这些内容保留扩展位置，不预先开发对应的通用框架。

## 3. 画面与空间方案

### 3.1 横版 2D 正侧视剖面（用户确认）

使用正交相机与侧面二维贴图。列车水平展开，车厢内部采用剖面，车顶在上方同时可见。人物在每层沿横向通道左右行走，通过舷梯上下。铁路、车底与转动轮轴在剖面下方可见。

此视角为用户明确要求。Three.js 使用正交相机承载二维平面，绘制顺序仅用于遮挡，不引入俯视角或透视深度。[S1]

车顶与车内各自是一张逻辑地图，共用同一节车厢的局部坐标，但具有不同的层标识。通过梯口、舱门等连接点建立跨层路径。

| 规则 | 实现方式 |
| --- | --- |
| 车顶与车内切换 | 切换主要显示层与可点击对象；另一层继续模拟 |
| 另一层有威胁 | 层切换按钮显示敌人数、受袭地点和告警 |
| 看不见的设施 | 不参与当前层的鼠标拾取，避免点穿车顶 |
| 跨层移动 | 必须经过连接点，并满足门状态、占位和权限条件 |
| 跨层攻击 | 首版默认禁止；只有明确设计的开口或连接点规则才允许 |
| 车厢之间移动 | 通过车厢连接处；车内连接与车顶连接分别定义 |

空间身份建议包含 `carriageId + layer + cellX + cellY`。人物实际移动位置可连续插值，设施占地和路径节点使用网格。

### 3.2 列车运动与人物寻路分离

车内和车顶模拟使用列车局部坐标。旅行系统记录当前线路、沿线距离、速度和到达时间；背景滚动、地景变化和轮轴动画呈现行驶。

列车前进不改变人物脚下的导航网格。进入车顶后的敌人也使用同一套列车局部坐标。登车跳跃先检查落点，再在落地时加入该层导航；首版用入场动画表现跳跃，不引入完整弹道物理。

停靠后，背景和轮轴按车速减速至停止，生活和生产仍继续。世界地图面板的打开本身不暂停模拟，玩家可手动暂停。

### 3.3 狭窄空间通行

初版使用双向横向通道寻路，跨车厢由连接器相连，跨楼层只通过舷梯节点。车内家具置于通道后方，不阻挡横向通行；车顶掩体可阻挡并被敌人破坏。

永久障碍由导航网格处理，人物临时占位由移动预约处理。站台工作位、床位、梯口使用容量约束；堵塞时执行等待、让行、改道或取消任务，并设置重试间隔。

必须尽早验证：两人在窄走廊迎面相遇、多人抢同一梯口、床边被家具占住、工作位不通、战斗中门被破坏。不能只测试空车厢里的单人寻路。

## 4. 工作、生活与直接控制

### 4.1 工作优先级

优先级建议采用：1 最高、4 最低、0 禁用。相同优先级按界面上工作类型的稳定顺序选择，再结合任务可达性、技能和距离决定具体任务；界面说明其含义。

调度只在任务完成、取消、资源变化、需求越过阈值等事件发生时，或低频复查时运行。人物不必每一帧重新考虑所有任务。

### 4.2 右键交互约定

| 选择状态与目标 | 菜单或行为 |
| --- | --- |
| 未选择人物，右键工作台 | 设置制作清单、查看材料与状态 |
| 选择普通人物，右键工作台 | 强制执行可用制作任务；也可进入制作清单 |
| 选择普通人物，右键床或食物 | 强制休息或进食；不可用时显示原因 |
| 选择普通人物，右键损坏设施 | 强制维修；列明缺材料、技能不足或不可达的原因 |
| 选择征召人物，右键地面 | 移动到可达位置；多人分配不同落点 |
| 选择征召人物，右键敌人 | 攻击指定目标 |
| 选择征召人物，右键梯口 | 通过连接点移动到另一层 |

制作清单先支持：制作 N 次、保持库存数量、持续制作、暂停、删除和排序。保持库存数量时计入现存成品与已承诺的生产量，防止多个工作台一起补货造成严重超产。

强制工作可以覆盖“该工作类型优先级为 0”的日常安排，但不能覆盖失能、技能门槛、缺失材料或不可达条件。命令有效性在下达与执行时均检查。

### 4.3 明确需求数值的方向

按需求中“数值低时自动恢复”的行为，内部统一使用 0—100 的饱食度和精力，100 表示充足，越低越紧急。界面建议也使用“饱食度”“精力”；如显示“疲劳程度”，则由 `100 - 精力` 转换，避免两种方向混用。

建议调试初值：饱食度低于 30 寻找食物，吃到 80 以上再退出；精力低于 25 开始休息，恢复到 85 再起床。开始与结束阈值不同，可减少反复切换。阈值和下降速率全部进入配置，不能视为已确定平衡值。

普通需求优先于普通工作。手动强制任务可以短期压过普通需求，但生命危险的饥饿/精力阈值可取消该任务并告警。没有食物时提示资源缺口并降低重试频率；没有可达床位时允许效率较低的地面休息。

### 4.4 征召行为单独定义

征召立即中断普通工作并释放相应预约，人物进入玩家控制状态。征召期间，普通饥饿和疲劳不会擅自取消战斗命令；需求继续消耗，并在极低时告警、施加惩罚，最终可导致失能。

倒地、死亡等不可行动状态覆盖所有命令。解除征召后重新评估需求和工作，不盲目恢复可能已经失效的旧任务。

建议行为判断次序如下：

1. 检查死亡、倒地和其他不可行动状态。
2. 已征召则执行战术命令，按需寻找可攻击目标。
3. 未征召且有紧急生存需求，则处理紧急需求。
4. 执行有效的强制生活或工作命令。
5. 处理普通进食、睡觉需求。
6. 按工作优先级领取任务；无任务则待命。

### 4.5 统一任务生命周期

任务依次经历：生成、校验、预约、移动、取料/准备、执行、交付、完成。任一步均可因资源变化、征召、设施损坏、路线失效而取消或等待。

预约需要覆盖物品数量、交互位置、工作台槽位、床位和必要的通道容量。任务中断要释放未使用预约；已取走的物资仍属于真实库存中的某一位置；已消耗原料与在制品状态必须保存，避免取消命令或读档造成物品复制。

## 5. 登车战

### 5.1 战斗流程

一次袭击包含：预警、落点选择、跳上车顶、车顶交战、破坏入口、进入车厢、车内交战、结束与清理。

敌人的目标选择建议为：

1. 优先攻击车顶上已感知、可到达或可射击的敌对人物，以及设计为可攻击的车顶设施。
2. 没有合理的车顶目标时，前往可破坏的入口。
3. 入口关闭则攻击舱门或阻挡设施；开启或破坏后进入车内。
4. 进入车内后攻击人物与列车关键设施。

“优先车顶”不应变成“永远追逐不可达目标”。设定追击超时、目标丢失和路径失败后的重新评估规则；已交战目标使用短暂锁定，防止频繁转身。

每个首版战斗场景保证至少一处可到达、可破坏的入口。发生异常而所有入口失效时，敌人转入明确的退却或结束状态，不能让袭击永久卡住。

### 5.2 最小战斗规则

首版采用实时可暂停战斗，具备移动、指定攻击、射程、视线、攻击间隔、生命、伤害、倒地/死亡、基础掩体和简化急救。弹丸首先是表现，命中与伤害按模拟时间计算。

视线和伤害按逻辑层校验，不能因为车顶隐藏就穿层攻击。关键设施损坏影响动力或生产；战斗结束后需要维修，形成物资和旅程上的后果。

敌人出现默认降到 1 倍速并告警；“出现敌人时自动暂停”作为玩家可选设置。短途演示可以采用固定波次，避免一开始就开发完整事件导演。

## 6. 旅行与经营如何形成闭环

首版至少有一次真实取舍：较短路线燃料消耗低但袭击风险高；绕路较安全却增加旅行时间、口粮和供暖消耗。玩家需要在出发前安排生产、补给与防御。

路线包含：起止节点、距离、基础限速、风险、环境、通行条件。列车包含：重量、动力等级、燃料、车体状态和供暖能力。首版只用这些少量变量建立影响关系。

地图按地区与线路保存状态，车站事件读取这些状态。尚未做复杂世界演化时，也不把所有内容写成互不关联的随机弹窗。

建议原型时间尺度：一个游戏日约等于 1 倍速下 8 分钟现实时间；一年暂按 120 个游戏日、每季 30 日配置。先验证短途旅行与生活节奏，再校准完整年循环。首版用短期寒潮和封线预报验证时间压力，不要求玩家实际等到下一个季节。

所有消耗、生产、战斗和事件使用统一游戏时钟。变速增加模拟步数；UI 动效可使用独立时钟，游戏暂停时不能继续扣饱食度、行程或弹药。

建议结束条件：完成指定迁徙目标为胜利；全员失去行动能力且没有恢复可能时失败。燃料耗尽首先让列车停驶并给出补救途径，不立即宣告失败；路线和节点配置需避免无预警的必死状态。

## 7. 技术架构

### 7.1 技术选型

| 模块 | 建议方案 | 目的 |
| --- | --- | --- |
| 工程 | TypeScript strict + Vite + npm 锁文件 | 编译、开发服务器、构建与依赖可复现 |
| 游戏显示 | Three.js 正交相机、贴图平面、图集、明确的绘制层级 | 表现二维场景、人物、选框、路径与轻量特效 |
| 管理界面 | React + HTML/CSS | 优先级矩阵、制作清单、人物详情与世界地图面板 |
| 模拟 | 独立 TypeScript 状态和系统 | 运行工作、生活、战斗、旅行，不依赖显示对象 |
| 导航 | 网格 A* + 连接点图 + 占位预约 | 车内、车顶和车厢间移动 |
| 动画 | 薄骨骼适配层 + Three.js 对象层级/AnimationMixer | 复用少量骨骼动作与人物换装 |
| 数据 | 带类型校验的内容定义；稳定内容 ID | 设施、物品、配方、人物、敌人、事件和路线配置 |
| 存档 | IndexedDB + JSON 导入导出 | 本地恢复、迁移、备份和问题复现 |
| 验证 | Vitest；关键用户流程采用 Playwright | 检验模拟规则及鼠标交互闭环 |
| 版本管理 | Git + GitHub | 可运行的里程碑、历史追溯和回退 |

这里的 Three.js 负责渲染与动画，任务系统、存档、寻路等由项目实现。官方游戏教程也明确区分 Three.js 与完整游戏引擎的职责。[S2] 不在规划中指定未经项目兼容性验证的“最新版”版本号；M0 选择相互兼容的稳定版本并提交锁文件。

### 7.2 状态流与模块边界

玩家输入先转换为命令，再由模拟系统验证和执行；模拟发布状态快照与事件，显示层和管理界面读取它们。

关键原则：

- 模拟实体用稳定 ID 引用，不保存 Three.js Mesh、DOM 或 React 组件。
- 同一份权威状态决定人物位置、物资、需求与战斗；界面不能私自修改库存。
- 使用普通实体表与按职责划分的系统即可起步，不引入大型 ECS 框架或完整行为树编辑器。
- 界面按事件或低频快照更新，不把逐帧人物移动写入 React 状态。
- 动画读取游戏结果；动画结束回调不能成为唯一的产出、命中或旅行结算来源。

建议模块位置：

| 路径 | 职责 |
| --- | --- |
| `src/app/` | 启动、场景切换、依赖组装 |
| `src/sim/` | 时钟、命令、实体、任务、需求、库存、建造、战斗、旅行 |
| `src/navigation/` | 网格、跨层连接、路径查询、占位与让行 |
| `src/render/` | Three.js 场景、相机、贴图、动画、拾取与可视化 |
| `src/ui/` | 工作表、右键菜单、制作清单、人物面板、地图、通知 |
| `src/content/` | 配方、物品、设施、事件、路线和初始场景定义 |
| `src/save/` | 序列化、版本迁移、校验、导入导出 |
| `public/assets/` | 实际运行使用的素材、图集、骨骼与动作数据 |
| `art/source/` | 经挑选的原图、分层源文件、生成说明与素材清单 |
| `tests/` | 模拟回归用例与浏览器关键流程 |
| `docs/` | 设计文稿、开发规划、操作规范、技术决策与验收记录 |

### 7.3 时钟、存档与复现

原型建议固定 20 Hz 模拟步进，显示层按浏览器帧率插值。人物需求、目标搜索等系统可以按较低频率运行；战斗与移动仍使用统一模拟时间。

加速时处理更多固定步，不放大单步时间。超出计算预算时降低实际加速并提示，不静默跳过模拟步。浏览器切到后台默认暂停，避免重新打开时补算一大段不可见的生存和战斗过程。

存档从 M1 起伴随功能开发，至少保存：版本、时钟、随机数状态、实体 ID、车厢与层、物品、设施、人物需求、工作优先级、制作清单、任务阶段、在制品、征召状态、战斗目标、线路进度和世界事件状态。

导航缓存和显示对象可重建。预约由已保存的有效任务确定性重建，并检查是否冲突；失效任务取消并保留已发生的资源变化。自动存档在稳定的模拟步边界生成快照。

使用可设种子的随机数、稳定的遍历次序与命令记录帮助复现问题。首版目标是同一运行版本中的可重复行为，不承诺跨浏览器或跨版本逐位一致的网络锁步。

## 8. 图片生成与骨骼动画制作流程

### 8.1 先做一套代表性素材

M0 就制作一个人物、一组车身/轮轴、一套床和工作台、一个车顶入口，用于验证视角、遮挡、缩放与动作。其余功能在统一占位图下推进，代表素材通过后再扩量。

建议美术方向为高可读性的手绘工业废土风格，有限色板、清晰轮廓、统一光照方向。实际风格尚未确定，先提供一张人物与车厢同屏的样板进行判断。

### 8.2 生成图片并不等于生成可运行骨骼

图片生成阶段负责外观；拆件、补全遮挡、统一比例、设置关节锚点、绑定骨骼和制作关键帧需要单独完成。工期必须计入这些整理工作。

建议资产流程：

1. 固定视角、比例、轮廓、色板和透明背景规范。
2. 生成角色基准外观与车厢样板。
3. 以统一参考生成或编辑头、躯干、上/下臂、腿、手持物等独立部件，保持关节周围足够的遮盖余量。
4. 校正边缘和大小，设置脚底基准点、骨骼锚点及绘制顺序。
5. 输出透明 PNG 源件、运行图集，以及包含骨骼层级/枢轴/动作的 JSON。
6. 在角色预览场景中检查四个朝向、行走、换装备、暂停和加速。
7. 进入真实车厢，检查家具遮挡、选中轮廓、车顶切换与缩放效果。

生成的大图或拆件图可能仍需修订。先通过一套样板再批量制作，避免大量不可绑定或视角不一致的素材。

### 8.3 骨骼方案

首版采用刚性分件的二维骨骼：图片部件附着于父子变换节点，关节按关键帧旋转/平移，外观随骨骼层级运动。可使用 Three.js 的对象层级或 Bone 节点承载关节，再用 AnimationMixer 播放动作；此处是项目实现方案，不是现成的完整二维角色工作流。[S3][S4][S5]

这种实现满足分件骨骼动作，不要求首版完成柔性蒙皮、复杂 IK、布料或专用动画编辑器。将骨骼读取、换装、朝向和动作切换封装为独立接口，后续有质量需求时再评估其他动画管线。

人物只做侧面分件，左右镜像改变朝向。非对称装备与手持物随骨骼朝向更新。仅横向行走，朝向跟随移动方向或攻击目标；换层时显示沿舷梯攀爬。

| 对象 | 首版动作 | 说明 |
| --- | --- | --- |
| 人物 | 待机、行走、工作、攻击、受击、倒地 | 进食可复用手部工作动作；睡觉先使用姿态与轻微呼吸 |
| 轮轴 | 转动 | 设置旋转骨骼/节点，角度随列车实际行驶距离累计 |
| 登车敌人 | 入场跳跃、行走、攻击、受击、倒地 | 跳跃复用角色骨架加根节点轨迹，不影响伤害判定 |
| 舱门 | 打开/关闭、损坏 | 简单关节运动或状态贴图即可 |

人物行走相位跟随实际局部位移，堵住时停止迈步；轮轴角度按距离/轮半径换算，停车即停止。动画外观插值可逐帧运行，但游戏暂停时角色与轮轴动作一并暂停。

### 8.4 素材管理

素材清单记录 ID、用途、尺寸、方向、脚底/枢轴位置、依赖的骨骼、生成说明和选定版本。保留精选原图与分层源文件；试验性废稿不进入运行目录。

图集与透明贴图需要检查边缘渗色、排序和遮挡。角色骨骼的每个分件可能增加绘制开销，M0 就测代表场景，后续按实际瓶颈采用图集合批、静态层合并和屏外动画降频。

## 9. 开发里程碑

工期假设：一名熟悉 TypeScript 的开发者持续投入；使用图片生成协助美术，包含基础素材整理，不包含多人协作等待或反复更换画风。以下是规划估算，不是交付承诺。

| 阶段 | 内容 | 可验收结果 | 估算 |
| --- | --- | --- | --- |
| M0：工程与关键验证 | 初始化工程和 Git；正交二维渲染、输入、时钟；双层地图、窄通道和一套骨骼样板；简要决策记录 | 一个人可跨车厢/梯口移动；两人不会在窄路永久卡住；同屏角色与车厢样板成立；基础构建通过并推送 | 2—4 人日 |
| M1：人物生活与列车基础 | 6 人、3 节车厢；选择、框选、需求、食物、床、基础库存；暂停/变速；基础存读档 | 连续运行 10 分钟能自动吃饭睡觉；无资源时有解释；存读档后需求、位置和物资一致 | 5—7 人日 |
| M2：工作与生产建设 | 优先级矩阵、右键制作清单、强制任务、搬运、预约、加工、建造、维修 | 原料到成品全流程可运行；抢同一资源、取消任务、拆设施等情况不复制或吞掉物品 | 6—9 人日 |
| M3：征召与登车战 | 征召、战术移动、近/远程、车顶目标、入口破坏、跨层入侵、受伤处理 | 可以守住车顶；也能演示失守后敌人进入车厢；解除征召后恢复生活；战斗可存读档 | 5—8 人日 |
| M4：旅行闭环 | 小型铁路网、路线选择、燃料、温度、预报、节点补给、车厢获取、胜负条件 | 至少两条路线各有代价；准备、旅行、袭击、维修、补给和抵达目标形成完整试玩 | 4—6 人日 |
| M5：首个可玩版本 | 完成代表范围的生成美术与骨骼动作、反馈音效、提示、平衡、性能与关键回归 | 20—30 分钟完整流程可重复完成；资源正确、主要操作可理解、性能与存档达到约定标准 | 5—8 人日 |

合计约 27—42 人日，加入约 20% 缓冲后约 32—50 人日，按单人每周 5 个工作日约 6—10 周。M0 之后根据视角、骨骼整理量与通行验证结果重估，不把原型估算外推为完整游戏工期。

M0 至 M5 顺序推进，每个里程碑都提交可运行版本。美术样板在 M0 开始，存档在 M1 开始，并随着 M2—M4 的新状态持续扩展。

## 10. Git 与交付规范

仓库地址规范化为 `https://github.com/casuak/train_v3.git`，默认分支采用 `main`。本轮已核对仓库可访问；按用户说明的空项目制定初始化步骤。

实施时先取得仓库当前状态并检查是否存在仓库级开发约定。若空仓库状态已经变化，应保留已有内容，再按实际基线工作。

建议使用短周期功能分支，例如 `feat/core-simulation`、`feat/work-orders`、`feat/boarding-combat`；`main` 保持可运行。每完成一个可验收的小功能就提交并推送，避免长期只在本地堆积。

首次工程提交应包括：工程配置、锁文件、README 运行说明、设计文稿与本规划、格式/类型检查、最小可运行场景以及持续集成配置。纯文档更新只需文档检查；行为代码进入主线前通过相应类型检查、核心测试和构建。

可采用的提交主题：

- `chore: initialize typescript threejs project`
- `feat: add train grids and pawn movement`
- `feat: add needs and work scheduling`
- `feat: add roof boarding combat`
- `docs: record development plan and milestone results`

完成首个完整试玩后创建 `v0.1.0` 标签。仓库内记录每个里程碑的操作方式、完成内容和已知限制；在实际推送成功后报告对应提交，不提前宣称已上传。

生成美术的运行素材与精选源文件纳入版本管理；`node_modules`、构建缓存和临时渲染文件忽略。出现显著的大型源素材后，再根据实际体积与协作方式配置 Git LFS，避免先引入不必要的流程。

## 11. 验证与性能标准

### 11.1 优先覆盖的行为风险

| 风险 | 验证场景 |
| --- | --- |
| 资源重复扣除或复制 | 两人竞争最后一份食物/原料；生产中征召；消耗后读档 |
| 任务无法释放 | 强制任务取消、工作台被拆、人物倒地、材料被移走 |
| 永久堵路 | 窄通道迎面、多人上梯、家具阻塞、门在移动过程中关闭 |
| 需求反复切换 | 阈值边缘、刚吃完立即工作、缺床、无食物 |
| 控制模式混乱 | 征召时不擅自找饭；解除征召后需求优先；多人命令落点有效 |
| 穿层攻击或错误点击 | 车顶遮蔽车内、层切换、关闭舱门、不同层同坐标人物 |
| 变速不一致 | 同一命令脚本运行到相同模拟 tick，比较不同显示速度下的关键状态 |
| 存档损坏或状态漏存 | 生产中、跨层移动中、战斗中、旅行途中分别保存并恢复 |

核心规则采用无渲染测试；右键菜单、工作矩阵、选择/征召与完整试玩采用少量浏览器流程测试。根据真实风险补充回归，不为每个展示组件重复写实现镜像测试。

### 11.2 性能预算

M0 记录参考设备、浏览器、分辨率与 DPR。后续所有性能目标都注明测试环境和人数规模。

建议首版测试规模：10 节车厢、30 名友方与 10 名敌人；目标是 1080p 下接近 60 FPS，3 倍速时模拟仍能维持目标推进速度，输入没有明显延迟。具体阈值以 M0 设备测量修订，不能当作已验证结果。

另建 100 人场景用于提前观察寻路、调度与分件动画增长趋势，不以此承诺原设计中 200 人的正式性能。

排查顺序：人物与设施查询范围、任务重新评估频率、路径重算次数、分件绘制调用、UI 刷新频率。只有测量证明主线程受模拟阻塞时，再考虑 Worker 等更复杂的分离方案。

## 12. 建议现在采用的默认决策

| 决策 | 本规划建议 | 后续校验点 |
| --- | --- | --- |
| 视角 | 正侧视二维贴图，车内与车顶同屏剖面 | M0 同屏样板检查人物、家具、轮轴与车顶可读性 |
| 空间 | 车内/车顶双层，梯口连接 | M0 验证；M3 检查战术操作 |
| 动画 | 刚性分件骨骼，四向外观，少量动作复用 | M0 验证绑定工作量和质量 |
| 初始规模 | 6 人、1 机车 + 3 车厢 | M1 检查调度与画面密度 |
| 地图范围 | 6—8 节点的短途迁徙 | M4 验证路线取舍 |
| 需求命名 | 饱食度与精力，低值触发恢复 | M1 操作和信息表达验证 |
| 战斗强度 | 小规模可暂停登车战 | M3 检查调度切换与战斗压力 |
| 内容节奏 | 先完成经营—迁徙—战斗闭环，再扩人物社会与世界演化 | M5 完整试玩评估 |

下一步实施从 M0 开始：完成工程、双层地图、狭窄通行和骨骼样板四项验证；通过后再扩大功能和素材数量。
